# 系统架构设计

## 1. 总体结构

系统采用前后端分离的 Web 架构。Nginx 负责外部 HTTPS 接入，C 语言业务服务负责证书管理业务，MariaDB 保存结构化业务数据，密码引擎负责密钥和签名等密码学操作。

主要组件：
- **Nginx：** 终止 HTTPS 连接、提供管理页面静态文件，并将 `/api/v1/` 请求反向代理到 C 服务的 Unix 域套接字。
- **C 业务服务：** 初期采用单进程、模块化结构，负责 API 路由、身份认证、权限控制、CA 与证书业务、数据库访问、密码操作和审计。
- **MariaDB：** 保存 CA 元数据、证书元数据、证书状态、申请记录、吊销记录及审计日志。
- **证书文件存储：** 保存 PEM、DER 证书对象及按安全策略生成的 P12 交付包；证书文件与数据库元数据分离存放。含私钥的 P12 属于敏感密钥材料，不能按普通证书文件管理。
- **密码引擎：** 初步采用铜锁（Tongsuo），通过内部适配层封装引擎接口。

## 2. 请求处理路径

浏览器 → HTTPS → Nginx → `/run/certservers/api.sock` → C 业务服务 → MariaDB、证书文件存储或密码引擎。

C 业务服务初期只监听 Unix 域套接字，不开放公网 TCP 端口。套接字建议使用专用用户和用户组，权限通常设置为 `0660`；其父目录不得允许无关用户写入。

## 3. 进程模型

初期使用一个 C 语言主服务进程，内部按 API、CA、证书、密码、数据库、审计和公共组件划分模块。只有在任务量、可靠性或资源隔离需求明确后，才考虑拆分定时任务或后台工作进程。

## 4. RADIUS 集成边界

RADIUS（远程认证拨入用户服务）负责网络接入认证；CA 负责证书签发、更新和吊销。两者不直接共享数据库。

推荐由 CA 生成 CRL（证书吊销列表）并通过 HTTPS 发布，RADIUS 定期下载、验证签名和有效期后更新本地缓存。若业务要求更及时的单证书状态查询，再评估 OCSP（在线证书状态协议）。

CRL 地址可通过证书中的 CDP（CRL 分发点）扩展发布，也可以在 RADIUS 服务器侧显式配置。实际采用哪种方式，取决于 RADIUS 软件、TLS 库和终端环境的支持情况。

## 5. 证书格式与密钥交付

证书签发结果以 X.509 证书为核心，PEM、DER 和 P12 是不同的编码或封装形式：
- PEM：便于 Linux 服务及工具读取，可分别导出证书、证书链和受保护的私钥文件。
- DER：二进制编码格式，适合需要二进制证书对象的系统。
- P12/PKCS#12：可将证书、私钥和证书链封装成单个受密码保护的文件，适合终端导入。

证书格式转换不应改变证书主体、公钥、序列号、签发者、有效期和签名。若申请者通过 CSR 提交公钥，平台并不持有对应私钥，因此不能凭空生成含有该私钥的 P12。需要含私钥的 P12 时，必须采用平台生成密钥或其他经过授权的密钥交付流程。

## 6. 信任域隔离

Nginx 管理网站使用的 HTTPS 服务器证书，与签发终端身份认证证书的 CA 层级分开管理。Web 管理入口的服务器身份、管理员登录身份和终端 EAP-TLS 身份属于不同信任用途，不应混用同一证书或密钥。

## 7. 核心术语

- **CA：** 证书颁发机构，负责签发和管理数字证书。
- **X.509 v3：** 常用的公钥数字证书标准版本，支持扩展字段。
- **CSR：** 证书签名请求，申请者提交公钥、主体信息及相关签名，供 CA 验证后签发证书。
- **CRL：** 证书吊销列表，记录在有效期结束前已被吊销的证书。
- **OCSP：** 在线证书状态协议，用于查询单张证书的状态。
- **P12 / PKCS#12：** 证书与可选私钥、证书链的封装格式，通常使用密码保护。


## 6. 领域模板与证书申请流程

平台在证书申请与签发之间增加领域模板和策略决策层。申请人先选择领域模板，系统根据模板版本生成表单，并将 LDAP 属性、系统生成值和用户输入映射到申请字段及 X.509 证书字段。

字段来源必须可追溯，至少区分系统生成、LDAP 自动获取、用户填写、用户选择和管理员锁定。模板负责默认值和规则，C 业务服务负责最终校验，不能信任浏览器提交的字段。

模板应版本化。申请记录保存模板 ID 和版本号，确保模板后续修改不会改变已提交申请的审批依据。

## 7. LDAP 身份验证与审批架构

LDAP（轻量级目录访问协议）服务器是外部身份目录。平台通过 LDAPS 或 LDAP + StartTLS 与其通信，先验证申请人身份，再读取策略允许的用户属性和组关系。用户密码只用于 LDAP Bind 验证，不保存到 MariaDB。

建议的业务链路：

申请人 → 选择领域模板 → LDAP 身份验证 → 读取授权目录属性 → 自动填充申请字段 → 提交 CSR/密钥生成请求 → 策略引擎 → 自动签发 / 人工审核 / 拒绝 → 证书交付。

策略引擎根据 LDAP 账号状态、稳定用户标识、用户组、领域资格、模板规则、字段修改情况、CSR 有效性及密钥交付方式进行决策。LDAP 身份验证通过不等于自动获得证书。

新增逻辑模块：
- **LDAP 适配模块：** 负责加密连接、服务绑定、用户搜索、用户 Bind 验证和属性读取。
- **模板管理模块：** 负责模板定义、字段映射、约束规则、版本发布和停用。
- **申请策略模块：** 负责自动签发、人工审核和拒绝决策。
- **审批模块：** 负责待审核队列、审批意见、审批人权限和审批审计。

LDAP 服务不可用或身份状态无法确认时，不得自动签发。LDAP 目录与 CA 数据库保持分离，平台只保存必要的身份关联标识和申请时属性快照。
