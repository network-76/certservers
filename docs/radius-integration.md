# RADIUS 与 CA 集成方案

## 1. 设计目标

RADIUS（远程认证拨入用户服务）负责网络接入认证；CA（证书颁发机构）负责证书签发、更新和吊销。两套系统应保持独立，通过标准化证书状态机制协作，而不是共享数据库或互相调用内部实现。

## 2. 推荐方案对比

| 方式 | 工作方式 | 优点 | 局限 | 建议 |
|---|---|---|---|---|
| CRL 文件分发 | CA 生成签名后的证书吊销列表，RADIUS 定期下载并缓存 | 标准成熟、实现简单、验证可离线完成、适合大量终端 | 吊销状态存在发布和下载周期的延迟；CRL 可能随证书数量增长 | **第一阶段首选** |
| OCSP 查询 | RADIUS 或其 TLS 后端针对证书序列号在线查询状态 | 单张证书查询及时，响应可较小 | 依赖在线服务；需处理超时、缓存、隐私和可用性；RADIUS/TLS 后端支持情况不一 | 后续评估 |
| 私有证书状态 API | RADIUS 调用 CA 提供的 HTTPS API 查询证书状态 | 可按业务需要扩展查询内容 | 需要自定义协议和客户端；增加耦合及维护成本 | 仅在标准机制不足时使用 |
| 直接访问 MariaDB | RADIUS 直接查询 CA 数据库表 | 表面上实现简单 | 数据库耦合、权限扩大、表结构泄露、升级困难，且绕过业务规则 | **禁止采用** |

## 3. 第一阶段：CRL 分发（推荐）

CRL（Certificate Revocation List，证书吊销列表）是 CA 对外发布的、由 CA 私钥签名的已吊销证书清单。验证方可使用证书颁发者的公钥验证 CRL 签名，并根据证书序列号判断是否已吊销。

### 3.1 数据流

1. 终端向 Wi-Fi 接入设备发起 802.1X 认证。
2. 接入设备将认证请求转交 RADIUS 服务器。
3. RADIUS 的 EAP-TLS 模块验证终端证书链、有效期、用途和签名。
4. RADIUS/TLS 后端根据证书的 CDP（CRL 分发点）扩展，或根据本地配置的固定 URL，找到 CRL 下载地址。
5. RADIUS 定期通过 HTTPS 获取 CRL，验证 CRL 签名、颁发者、有效期和 CRL 编号。
6. RADIUS 将验证通过的 CRL 缓存到本地；认证时检查证书序列号是否在吊销列表中。
7. 若证书已吊销，认证应失败；若 CRL 缺失或过期，则按预先定义的安全策略处理，不得无意间跳过吊销检查。

### 3.2 CA 侧需要实现

- 为每个 CA 维护独立的 CRL 策略和编号。
- 支持按吊销事件触发更新，也支持定时更新。
- 为 CRL 设置合理的有效期和下一次更新时间（Next Update）。
- 生成 CRL 后使用对应 CA 私钥签名。
- 通过 HTTPS 提供稳定、可访问的下载地址。
- 保留 CRL 版本、生成时间、下次更新时间、签名者和发布结果等审计信息。
- 证书中可写入 CDP 扩展，指向对应 CRL 地址；也允许 RADIUS 端通过本地配置指定下载地址。

### 3.3 RADIUS 侧需要实现或配置

- 配置受信任的 CA 证书链。
- 配置 CRL 获取方式、下载周期和本地缓存目录。
- 验证 CRL 签名及其颁发者，不能只检查 HTTP 下载是否成功。
- 检查 CRL 的有效期和版本，避免回滚到旧 CRL。
- 明确 CRL 过期、下载失败、缓存缺失时的处理策略。
- 验证实际 EAP-TLS 后端是否启用了客户端证书吊销检查。仅发布 CRL 并不代表 RADIUS 自动执行检查。

## 4. 第二阶段：OCSP 在线查询

OCSP（Online Certificate Status Protocol，在线证书状态协议）允许验证方针对某张证书查询状态，常见结果包括 good（未发现吊销记录）、revoked（已吊销）和 unknown（状态未知）。

如采用 OCSP，需要进一步确定：

- OCSP 响应服务由 CA 平台提供，还是由独立状态服务提供。
- OCSP 响应是否由 CA 直接签名，或由受授权的 OCSP 响应者签名。
- RADIUS 的 TLS 后端是否支持 OCSP 查询及响应验证。
- 超时和服务不可用时的处理策略。
- 响应缓存时间、签名证书更新和服务高可用方案。

OCSP 不应被假定为所有 RADIUS/EAP-TLS 实现都默认支持，必须针对目标软件版本实测。

## 5. 私有状态 API 的使用边界

若标准 CRL/OCSP 无法满足业务需求，可以提供只读证书状态 API，例如：

- `GET /api/v1/certificates/{serial}/status`
- 响应包含证书序列号、签发者标识、状态、状态更新时间和必要的吊销信息。

该接口仅作为补充机制。建议使用 HTTPS，并通过双向 TLS（mTLS，即通信双方都验证对方证书）或强身份凭据进行认证；实施最小权限、访问审计、限流和超时。API 不应暴露私钥、无关主体信息或内部数据库结构。

## 6. 故障策略

必须明确区分以下状态：

- **有效且未吊销：** 证书链、用途、有效期和吊销状态检查均通过。
- **已吊销：** 明确拒绝认证。
- **状态未知：** 无法确认状态，应按部署的安全等级和策略处理。
- **CRL 过期或不可用：** 不能将其误判为“证书未吊销”。

对于企业 Wi-Fi 身份认证，建议默认采用 fail-closed（故障关闭）策略：吊销状态无法可靠确认时拒绝认证或进入明确的受限处置流程，而不是静默放行。若业务选择 fail-open（故障开放），必须经过风险评估、明确授权并记录审计。

## 7. 重要的互通性验证

需要在实际部署组合中验证：终端 supplicant、RADIUS 软件、EAP-TLS 模块、TLS 库、国密密码提供程序、证书链和 CRL/OCSP 检查。证书格式符合 X.509 标准，并不能单独证明完整国密 EAP-TLS 链路可用。
